4a — the worker runtime and the message protocol

Two questions, and the second one is the harder to measure honestly. Does a run in the browser give the same verdict as the same run natively? And does the page stay alive while it runs?

0. The instruments, before any reading

Three of the four things that went wrong in the measurement slice were measurement bugs producing plausible numbers, not code bugs producing errors. So the instruments report on themselves first.

1. Boot

The runtime is vendored, not fetched from a CDN, so the bytes are the ones the measurements were taken against. The wheel is rebuilt by web/serve.py on every start and its hash is shown here: a stale wheel runs old code, passes every check, and says nothing.

2. The verdicts

The native answers in expected.json were computed by the process serving this page — same commit, same machine, same NumPy — rather than pasted in from a previous session.

3. Is the page alive?

Identical work, run twice: once inside the worker, once on the main thread. The main-thread arm is the baseline, taken in this session, because absolute timings on this machine swing up to 4x within one — so a comparison against a recorded number would not mean anything.

The square below is a CSS animation driven by the main thread. It stops for exactly as long as the main thread is blocked. Watch it during each arm.

4. What does chunking cost?

The slice concluded that a stepping loop "may be chunked as finely as the UI wants", from 4 096 boundary crossings costing less than the noise on a single workload. That measured a synchronous split. A streaming UI does something different: it chunks and yields, so the worker thread is descheduled and resumed once per chunk, and it drains and posts what it recorded. This sweep separates the three.
