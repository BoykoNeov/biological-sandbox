Every model in the registry, in the browser

The demo page runs one model. This one runs all fourteen, and it does not know anything about any of them: the list, the capabilities and the parameter fields below are all asked for at run time, from the same registry the test suite uses. Adding a model to the project adds it here, with no change to this page.

Nothing on this page is asserted anywhere. It is a way to look at the models, not a way to check them. What is checked is checked natively, against a tolerance derived from the statistics of the measurement — see the demo for what a real verdict looks like, and why one of these models refuses to produce one.

1. Pick a model

parameters

Plain JSON, because that is what a spec is — the project's Experiment named by a string and carrying a dict. Edit it and run.

what this model accepts

Read out of the registered parameter class itself, so it cannot drift from what the model actually takes. A field with no default is one you must supply.

2. Watch it run

the field

This model carries a 2-D field, so there is a picture as well as a trace. The colour range is printed beside it: an image drawn with a silently autoscaled range makes a claim about shape while hiding one about magnitude, and a pattern collapsing to nothing looks identical to one at full strength if the scale follows it down.

3. The check, where there is one

Six of the fourteen have a closed-form prediction the ValidationSuite can compare a run against. The rest do not, and the button says so rather than going quiet — a model whose limit is a cycle has no single number for an ensemble mean to match, and that is a fact about the model, not a gap in the page.
